Move 01 · Ground it

Designed from the floor, not the canvas.

Everything starts from the scenarios the system runs in. Two contexts pull opposite ways — and those tensions, not aesthetics, set the rules.

Operational environment

Glance & act — speed wins

On the floor, staff act under pressure. Every extra control is a delay; the UI has to be fast and unambiguous.

Back office

Review & decide — clarity wins

Shared, data-dense work. Legibility and structure matter more than density.

balance clarity ⇄ speed in every component many terminal sizes — design for widest reuse some flows must port to touchscreen later

Move 02 · Constrain

I’ve watched one button become four.

Leave every option open and the same “Save” drifts — a different size here, a different shape there. Nobody can hold it consistent.

Open — the same Save, drifting

Four takes on one action. Now multiply by every screen and team.

Governed — one Save, everywhere

One shape, one token — only the size flexes, for floor vs back office.

Every option has to earn its place — so I gave the system a layer that decides which ones do.

Move 03 · Govern in code

The layer most systems skip.

Most
tokens→ components→ app
Mine
tokens→ capability→ whitelist · governance→ app

Most systems keep the rules in a doc. I made the approved set a layer in the system itself — and everything else follows from it:

  • Composed from axes. variant × color × size, one rule — color is the accent.
  • One source, derived. the catalog generates the developer’s types and the designer’s docs (live in Storybook) — they can’t fall out of sync.
  • Centralized handoff. I push to git; devs diff design-lib vs app-lib and sync on their release.

Move 04 · Enforce & deepen

Governance the compiler can’t ignore.
